How the whole system fits together

A simulated marketplace produces hourly numbers. The brain (brain/) reads them, notices a change, finds the place and the cause and writes an incident report. It also takes in new metric definitions while it runs. A console shows what the brain found. Around them: a way to put faults into the world, and scripts that score the brain against the truth. This page covers the world, the console and the scoring; the brain has its own page: brain-architecture.html.

The parts

Every part on the picture exists in the code and has tests. The middle column of the live run shows the files that the brain and the console exchange. The brain opens the database read-only, and SQLite lets it read 4 tables: facts_hourly, ingestion_log, releases, calendar. The table ground_truth is refused to it. The brain imports nothing from sim/ or ui/, and the console imports nothing from brain/: they meet only in the database and in those files. The console shows the example incident from docs/contracts/incident_example.json, marked as an example, only while the incidents folder does not exist. The brain creates the folder when it starts; from then on an empty folder means that nothing was found.

The brain is one process, python -m brain.run. The metric graph holds the metrics, their formulas and the possible causes; it is validated against the data before its export is written. Every hour the monitor judges the newest hours of every watched rate. For each open incident the investigator finds the place, the cost in EUR and in orders, and the cause, and records every question and its answer in a trail. Each incident is one file, incidents/*.json, that is updated in place while the incident is open, ongoing and then resolved. The extension agent takes in new metrics while the brain runs (see the console). The brain has 20 modules and 6,624 lines; brain-architecture.html describes them.

What the world contains

One row per hour and segment. A segment is a combination of country (4), platform (3), category (5), channel (3): 180 segments. The purchase funnel is built from counts and rates, so the graph's formulas hold exactly in the data: sessions, product views, add to cart, checkouts, payment attempts, payment successes, orders, then money.

Columns (19): sessions, searches, search_clicks, feed_impressions, feed_clicks, product_views, add_to_cart, checkouts, payment_attempts, payment_successes, orders, gmv, discounts, marketplace_fees, refunds, ad_impressions, ad_clicks, ad_spend, stockouts. Sources that report data: traffic, search, recommendations, orders, payments, ads, inventory.

Daily and weekly rhythm, a slow trend, one shared shock per country and hour, and the noise of small counts. At the row level 91% of rows have fewer than 5 payment attempts, so a single row can show a rate of 0.0 or 1.0 by chance; see data-granularity.md for what each level of aggregation can and cannot show.

Every injection is written to ground_truth with its full settings, so it can be replayed. A rollback sets the end of an injection; for a fault that came with a release (payment, search, ad budget) it also writes a rollback release. The same fault with the same settings cannot be recorded twice. What the brain reported for each kind of fault is in results.md.

Why one change moves nothing else

Every value in an hour gets its own uniform random number, drawn up front, and is turned into a count through the inverse distribution. A change to one segment's rate therefore changes only that segment's values: the random numbers of every other segment stay where they were. Backfill, live mode and replaying an injection give identical rows wherever the injection does not reach. The tests compare whole tables row by row to prove it.

The console

The main console (/, ui/static/v3/) is a canvas. The header holds the clock, the incident counts, the domain selector and the Test bench. The graph fills the page and can be dragged and zoomed; it shows the formula tree, coloured by incident status, and picking a domain keeps that domain's boxes and their path to the top. The incidents are cards in a dock along the bottom, live ones first. A click on a card lights the incident's path on the graph, with the change of each moved metric and "held" on each factor that stayed normal, and opens its report in a panel on the right; a click on a metric opens its definition there. Replay the investigation walks the incident's trail on the graph one step at a time: each step rings the metrics it touched, leaves a numbered pin and shows its result, and the same step is lit in the report's trail. The Test bench, marked DEMO, holds the controls that write simulated faults, end them (a rollback) and hand in a new metric. The classic console (/classic, ui/static/index.html) shows the same data and controls with the graph and the incidents side by side and the DEMO bar folded at the top. The Data page browses the tables read-only.

The console draws the graph from the brain's graph export, the JSON file that the variable GRAPH_JSON names. The demo sets it to data/graph.json. The brain writes that file when it starts (--graph-out) and again whenever the graph changes. Without the variable the console reads the tracked example export docs/contracts/graph.json, which does not change at run time. The console asks for the graph, the incidents and the clock every 2 seconds.

A new metric at run time. The button Add refund_rate in the Test bench sends a definition (a name and a query; the agent finds the formula itself) to the console's API, which saves it as incoming_metrics/<name>.yaml. The brain's extension agent looks into that folder on every poll, checks the definition against the data and answers in incoming_metrics/<name>.result.json: a status (validated, tentative or rejected), one sentence for a person, and every check with its numbers. When the metric is accepted, the brain writes the graph export again, and a rate of two columns is watched from the next tick. The console shows the sentence and, on its next refresh, the new graph.

Scoring

python -m sim.score generate builds the database of one scoring run (default data/eval.db): 12 random faults, 8 innocent events (promos and late data) and one routine release per day over 49 days. It leaves 21 clean days before the first event. After them every event has a slot of its own, so two events never overlap.

python -m brain.run --replay --db data/eval.db --incidents eval_incidents --fresh walks that database hour by hour, as if it were live, and never reads a row from the future. It writes its incident files to a folder of their own; the live incidents/ folder is never used for scoring.

python -m sim.score score scores one run. It compares the incident files (default folder eval_incidents) with ground_truth and writes the report of that run to data/eval-results.md: faults detected, delay, localization, the right cause, false alarms, and how many innocent events stayed silent. An incident counts for a fault only when it is first seen inside the fault's window (up to 6 hours after its end) in a place that does not contradict the fault's, and it counts for one fault only. Records with the status explained or pending are neither a detection nor a false alarm.

python -m scripts.summarize_evaluation (scripts/summarize_evaluation.py) scores many runs with the same function. It writes docs/results.md and, beside it, docs/results.json with everything that page is rendered from. Holdout seeds get a line of their own. False alarms are counted per watched day there: the days of data without the hours of each run that pass before the replay's first judgement.

Localized and correct supported cause are counted among the detected faults; a cause counts only when the report names it as supported. The delay is counted in hours from the first affected hour. Watched days leave out the first 80 hours of each run, before the replay's first judgement. Over all runs, 6 detected faults have a report that does not support the right cause: stockout_surge (6).

Holdout means new random seeds of the same simulator: the same four fault kinds (three of each per run), the same ranges of severity and duration and the same scoring rules as the runs the brain was built on. It does not test other kinds of fault, other sizes or another scorer. The 10 holdout seeds were generated and replayed once for that page: no version of the brain was run on them before. The team states this; the scripts cannot check it. The other 10 seeds were also run while the brain was built, so their numbers are not independent. The other limits are listed at the end of results.md.

Not built

  • A euro threshold for alerts. A change is judged by its size against the rate's own history, not by what it costs.
  • Judging volumes such as sessions. Only rates are watched.
  • Formulas with constants, or with more than two metrics, in the search for the formula of a new metric.
  • Proposing cause links for a new metric. A definition can declare such links itself.
  • A range around the cost of an incident. The cost is one estimate, and it is noisy for a short incident in a small place.
